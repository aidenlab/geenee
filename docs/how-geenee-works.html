How geenee works

Seven parts, on four servers and one computer, cooperate so that a model can drive igv and Juicebox from one conversation. This document shows what each part is, which wires join them, and what crosses each wire.

The parts and the wires

The Host’s request to geenee comes from Anthropic’s or OpenAI’s servers, not from the person’s computer. That is why geenee needs a public https:// address even during local development.

Two things carry the whole design. First, geenee contains neither tool set: it forwards each tool call to the Upstream that owns it, and neither Upstream knows geenee exists. Second, an Upstream cannot answer by itself. It has to reach its Viewer, a web page in the person’s browser pane, and it does so over a WebSocket that the Viewer opened when it loaded.

So a single request from the model crosses three wires on the way out (A, then B or C, then D or E) and the same three on the way back. Everything else in the figure exists to set those wires up and to keep the person’s view in step with them.

Two wires are missing on purpose. The Workspace never speaks to the Viewers it frames: each frame is a window onto another site, and the Viewer inside behaves exactly as if it had been opened on its own. And geenee never speaks to a Viewer: it reaches one only by asking its Upstream.

One Room id, three Rooms

A Room ties one conversation to its Workspace and to the two Viewers inside it. open_geenee mints a Room id, ten Crockford base32 characters, and the model passes it back on every later call. The same id then names a Room in three places, and each place learns it differently.

The Juicebox Upstream predates the room argument. It acts on the Room of the call’s MCP session, and an unbound session’s Room is the one whose id is the session id. geenee exploits that by sending the Room id as the session id.

The igv Upstream takes the Room id as an argument, as it was designed to. The Juicebox Upstream takes no such argument, so geenee hands the id over in the session header instead, and the Juicebox tools gain the protection of a Room the model carries.

The Room id comes from the model on every call rather than from the MCP session because a Host does not keep one session per conversation. Claude desktop moves a conversation to a second session after the model first uses the browser pane. The model is the one thing that stays with the conversation.

Scenario: “open geenee”

The person types “open geenee”. The model calls open_geenee, and seven steps later both Viewers are connected and both marks are filled. Only the first step involves the model.

WireWhat happens
1AThe model calls open_geenee. geenee mints a Room id and replies with it and the Workspace link, https://geenee-view-dev.3dg.io/?room=7KQ2M9XA4T. Neither Upstream is contacted. The reply tells the model to open the link in the Host’s browser pane and to pass the Room id on every later call.
2IThe Host opens the link in its browser pane. The pane fetches the Workspace page from geenee.
3HThe Workspace opens a WebSocket to geenee’s Room. If a tool has already been used in this Room, the Room says which Viewer at once.
4J, B, CThe Workspace asks geenee for /viewers. geenee calls each Upstream’s own open tool for the Room and passes back the Join link from each reply. These tools are hidden from the model; only geenee calls them.
5F, GThe Workspace puts each Join link in a frame. Each frame fetches its Viewer page from that Viewer’s static site.
6D, EEach Viewer reads the Room id from its own address and opens a WebSocket to its Upstream’s Room. From now on its Upstream can push commands to it.
7J, B, CEvery 4 s the Workspace asks /connections. geenee asks each Upstream with a tool that changes nothing, reads the reply, and the Workspace fills or empties each mark.
The two status tools were never designed as a contract. geenee reads an error from read_session_summary as “not connected”, and looks for Browser Connected: Yes in the text of get_server_status.

Steps 3 and 4 start together, and so do the two halves of steps 4, 5 and 6. The figure draws them one after the other only so that each can be read.

Scenario: “go to MYC”

With geenee open, the person asks to go to MYC. The model picks igv_go_to_gene from the tool list, because igv is the Viewer for genes and loci. The call travels out along A, B and D, and its answer returns along the same wires.

WireWhat happens
1AThe Host posts tools/call for igv_go_to_gene with gene and room. geenee checks the Room id and picks the igv Upstream from the igv_ prefix.
2Bgeenee asks the igv Upstream for its tools, to find the Upstream’s own name for this one, go_to_gene. geenee keeps nothing between requests, so it asks every time; a change to an Upstream’s tools therefore needs no geenee release.
3H, BTwo things at once. geenee tells the Room that igv was used, and the Room tells every Workspace in it, which brings the igv tab forward. And geenee sends go_to_gene to the igv Upstream with the Room id as room.
4DThe igv Upstream’s Room pushes the command to the Viewer and waits up to 15 s for an ack.
5igv.js moves to MYC. Any sequence or track data it needs comes directly from the data hosts, not through any of the servers here.
6DThe Viewer acks with igv.js’s result and its new Session summary.
7BThe igv Upstream replies to geenee with the tool result.
8Ageenee rewrites any tool names in the text (read_session_summary becomes igv_read_session_summary) and returns the result to the Host. The model turns it into its answer.
geenee gives an Upstream 30 s, longer than either Upstream waits for its Viewer (15 s for igv, 10 s for Juicebox). A slow Viewer is therefore reported by its Upstream, in its own words, and not by geenee.

The Workspace is told in step 3, alongside the call and not after it, so that the right Viewer is already in front while it redraws.

Some tools never reach a Viewer at all. The search tools look things up in catalogues, and the Upstream answers from its own data. For these the path stops at the Upstream: A, then B or C, and back. The Workspace still brings that Viewer forward, because any forwarded call counts as using it.

What each part keeps

Most of the parts keep nothing. The table says what survives between requests, and where. The Viewer is the source of truth for what is on screen; everything else is a mirror or a pointer.

PartKeepsFor how long
The modelThe Room id, in the conversationAs long as the conversation
geenee, at /mcpNothing. Each request gets a fresh MCP server.
geenee’s RoomThe sockets of its Workspaces, and the last viewerUsed reportThe report is never deleted
igv Upstream’s RoomThe Viewer’s socket, its latest Session summary, and its last SessionDeleted 24 hours after the last message, unless a Viewer is still connected
Juicebox Upstream’s RoomThe Viewer’s socket, and its stateExpires after 24 hours idle
WorkspaceWhich tab is in front, and the number of the last report it acted onUntil the page closes
ViewersThe genome, locus, tracks, map and everything else on screenUntil the page closes; restored from the Room when reopened

When something goes wrong

What happensWhereWhat the model or the person sees
A call carries no Room idAgeenee refuses it, and says to call open_geenee and pass the Room id.
One Upstream cannot be reachedB or CIts tools drop out of the list; the other Viewer’s tools still work. A call to one of its tools gets an error that says so.
An Upstream refuses a callB or CThe Upstream’s own message, passed back as an error for the model to correct.
No Viewer has joined the Upstream’s RoomD or EThe Upstream answers that a Viewer must be opened first. The tab’s mark is hollow.
The Viewer does not ack in timeD or EThe Upstream reports the command as sent but unconfirmed.
The Workspace’s socket dropsHThe Workspace rejoins after 1 s, 2 s, up to 5 s. Meanwhile the tabs still work by hand.
geenee cannot reach a Viewer’s Upstream for /viewersJThat panel says the Viewer could not be reached, and to reload.

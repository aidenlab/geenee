Cloudflare, for an Apache hand

With Apache there was one machine, and everything lived on it. On Cloudflare there is no machine of yours. There are three kinds of thing you upload, and each does one job. This page explains what Workers, Pages and Durable Objects are, why geenee uses each one where it does, and how they replace what Apache did.

The short answer

  1. A Worker is a function. Cloudflare calls it with a request, and it returns a response. Nothing of yours keeps running between requests. geenee and the three Upstreams are Workers.
  2. A Pages project is a folder of files. You upload a built dist/ and Cloudflare serves it, the way Apache served DocumentRoot. No code of ours runs. The three Viewers are Pages projects.
  3. A Durable Object is a small, single object that holds state. For each name, such as a Room id, exactly one exists in the world. A Worker sends its requests to it. It keeps its own storage and can hold WebSockets open. Every Room is a Durable Object.

Workers and Durable Objects run your code. Pages serves your files. A Worker can carry files too: geenee’s Workspace page ships inside the geenee Worker.

From Apache to Cloudflare

In the Apache days you rented a machine and pointed a DNS A record at its IP address. You put HTML in /var/www, described the site in httpd.conf, and restarted. When you needed something dynamic, a PHP script or CGI program ran on that same machine. Its memory, its disk and its log files all belonged to you, and so did the job of keeping it up.

Cloudflare removes the machine. You upload code and files to your account, and Cloudflare copies them to every one of its data centers. A request is answered by the data center nearest the person who made it. Nothing is started, restarted or patched. In exchange, two things Apache gave you for free are gone: a disk you can write to, and memory that lasts from one request to the next. Durable Objects exist to give some of that back.

A Worker: code, not a server

A Worker is a module that exports one function, fetch. Cloudflare calls it with each request that arrives at the Worker’s address and sends back whatever it returns. This is geenee’s, trimmed:

export default {
  fetch(request: Request, env: Env): Promise<Response> {
    geenee ??= createGeenee({ igvUpstream: env.IGV_UPSTREAM_URL, … })
    return geenee(request)
  },
}

Three things here are new to an Apache hand.

  • There is no listen 443. You never open a port or start a process. Cloudflare starts a lightweight sandbox, called an isolate, in milliseconds when a request needs one, and throws it away when it likes.
  • env is the configuration. Everything the Worker is connected to comes in through it: the variables from wrangler.toml (the Upstream addresses), its static files (env.ASSETS), its Durable Objects (env.ROOM) and any secrets. These are called bindings.
  • Memory is a cache, never a store. geenee ??= builds geenee once and reuses it while the same isolate lives. That is safe because nothing in it changes. Anything that must last, such as who is in a Room, cannot live here: the next request may land in another isolate, in another city.

A Worker answers at the custom domain named in wrangler.toml. Cloudflare can also give every Worker a *.workers.dev address and preview addresses. We switch those off, so each Deployment has exactly one public address.

Pages: a folder of files

A Pages project is the closest thing on Cloudflare to Apache serving /var/www. Each Viewer is a Vite build, a folder of HTML, JavaScript and CSS. The Upstream’s deploy script uploads it:

wrangler pages deploy viewer/dist --project-name igv-viewer --branch main

Cloudflare serves those files at https://igv-viewer.pages.dev/ until the next upload. Our Viewers have no server code. Pages can run code, through Pages Functions, but none of ours do. All a browser fetches from Pages is the page itself, once, when a Viewer’s frame opens. After that, the Viewer talks only to its Upstream Worker.

Two Pages habits to know:

  • Every upload also gets its own address, such as https://3f9c1a2b.igv-viewer.pages.dev. Uploading with --branch main is what makes it the live one at igv-viewer.pages.dev. The old uploads stay reachable at their own addresses, which is handy for comparing.
  • Settings in the dashboard do not reach the build. A Viewer has to know its Worker’s address, and Vite fixes that address in the JavaScript when it builds. So the deploy script passes it in at build time (VITE_SERVER_URL), and checks the built files contain it before uploading.

Cloudflare now suggests Workers with static assets for new sites rather than Pages. Pages still works, and the Viewers stay on it.

A Durable Object: where state lives

Workers forget. Something has to remember that Room 7KQ2M9XA4T exists, when it was last used, and which Workspaces are connected to it right now. That is the Room Durable Object.

  • One per name, worldwide. env.ROOM.idFromName(room) always reaches the same object, from any Worker isolate in any city. It runs in one data center, chosen near where it was first used.
  • One request at a time. It handles its requests in turn, so two tool calls for the same Room cannot trample each other.
  • It keeps WebSockets. A Worker cannot hold a socket for long, but a Durable Object can. The Workspace’s /ws, and each Viewer’s connection to its Upstream, ends in a Durable Object.
  • Its storage outlives its code. A deploy replaces the class’s code, but every Room’s stored data stays. The [[migrations]] block in wrangler.toml is how you tell Cloudflare that a class was added, renamed or removed. It is the one part of a deploy that changes stored data, so treat it like a database migration.

The Upstreams have their own Durable Objects for the same reason: igv and Spacewalk each have a Room, and Juicebox has WebSocketRoom and McpSession. Each Upstream keeps its own Room for the same Room id. These are separate objects, and geenee never reads another Upstream’s Room.

Following one request

When a request arrives for geenee.3dg.io, Cloudflare’s DNS answers with an address belonging to Cloudflare, not to a machine of ours. The data center nearest the caller receives the request, sees the hostname belongs to the Worker geenee, and runs it there. That is the whole of what <VirtualHost> and ServerName used to do. There is no server behind Cloudflare: the Worker is the origin.

Why each piece is where it is

Workers, for geenee and the UpstreamsEach one has to run code on every request: answer MCP, forward calls, accept WebSockets. Files cannot do that.
Pages, for the ViewersA Viewer is a browser app. Its code runs in the person’s browser, not on Cloudflare. It needs a host for its files and nothing more.
Static assets, for the WorkspaceThe Workspace page could have been a Pages project. It ships inside the geenee Worker instead, in the same wrangler deploy, so the page and the code it talks to can never be out of step.
Durable Objects, for RoomsA Room has to be one thing, in one place, that every request for that id reaches, and that keeps its sockets open. Only a Durable Object is like that.

An Upstream and its Viewer are a pair that point at each other. The Worker’s VIEWER_URL names the Pages address, and its VIEWER_ORIGINS lets only that page open /ws. The Viewer has the Worker’s address built in. That is why each Upstream’s deploy script uploads both, and why they are always released together.

wrangler.toml is your httpd.conf

Secrets never go in this file. They are stored on Cloudflare with wrangler secret put NAME --env prod and reach the code through env like any other binding. geenee has none. The igv Upstream has one, SESSION_HMAC_SECRET.

Pages projects have no wrangler.toml in our repos. The project is created once, by wrangler pages project create in the Upstream’s deploy script, and each upload just names it.

The commands

The deploy scripts run the uploads for you, after their checks. The rest are for looking around, and take a Worker by name: geenee, geenee-dev, igv-mcp, igv-mcp-dev …

# upload a Worker: its code, files and settings
wrangler deploy --env prod
# upload a folder to a Pages project
wrangler pages deploy dist --project-name igv-viewer --branch main

# live logs from a Worker, like tail -f
wrangler tail geenee
# what was uploaded, and when
wrangler deployments list --name geenee
wrangler pages deployment list --project-name igv-viewer
# back to the previous upload, in seconds
wrangler rollback --name geenee
# which login and account you are using
wrangler whoami

geenee is the one exception to --env. It builds with Cloudflare’s Vite plugin, which picks the environment at build time: npm run deploy:prod builds with CLOUDFLARE_ENV=prod, then runs a plain wrangler deploy of what was built. The Upstreams use wrangler deploy --env prod.

wrangler rollback is the emergency brake. It puts back the previous code, but not the repo, and not the tag. The proper rollback is to release the earlier tag, as geenee’s Deployments describes.

In the dashboard, Workers and Pages projects share one list, Workers & Pages. You can tell Pages projects by their pages.dev address. The custom domains appear under the 3dg.io zone’s DNS as records of type Worker. Leave them alone: Wrangler owns them.

What Apache never asked of you

  • No disk. A Worker cannot write a file. What must last goes in a Durable Object’s storage.
  • No memory you can trust. A variable set on one request may be gone on the next. Cache only what you could rebuild.
  • A deploy is all at once, everywhere. There is no moment when half the servers run the old code. A bad deploy is also everywhere at once, which is why prod changes only from a tag that was tried on dev first.
  • Named environments inherit very little. [env.prod] does not get the top level’s vars or durable_objects, which is why wrangler.toml repeats them. Forget one and that Deployment silently lacks it.
  • The top level of wrangler.toml is never deployed. It is for npm run dev. Its name is geenee, the same as production, so deploying it by hand would put its settings, with the dev Upstreams, over geenee production. Use the scripts.
  • A Pages build cannot read dashboard settings. Anything the Viewer needs to know is fixed when it is built.
  • WebSockets are not covered by CORS. An Upstream checks the Origin of every /ws itself, against VIEWER_ORIGINS. A Viewer at a new address cannot connect until that list names it.

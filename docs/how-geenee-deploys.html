How geenee deploys

One run of scripts/deploy.sh or scripts/deploy-dev.sh replaces exactly one Cloudflare Worker: its code, the Workspace page it serves, and its settings. The Worker’s Durable Object storage is kept. Nothing that belongs to igv, Juicebox or Spacewalk is touched. This document shows what is uploaded, what is replaced, what survives, and what to run when you change something elsewhere.

The short answer

Say you run scripts/deploy.sh prod-2026-11-12, which releases that tag to geenee production, the published Connector. This is what changes on Cloudflare:

Replaced

  • The code of the Worker geenee: /mcp, /viewers, /connections, /ws, /versions, the tool renaming, the server instructions, open_geenee.
  • The Workspace page: index.html and its JavaScript and CSS, served by the same Worker.
  • The Worker’s settings: the three Upstream addresses, the binding to the Room Durable Object, logging.
  • The code of the Room Durable Object, which is part of the Worker.
  • The version the Connector, the Workspace and /versions report.

Kept

  • Every Room’s storage: the last “Viewer used” report.
  • Room ids. A Room id the model already holds still finds the same Room.
  • The custom domain geenee.3dg.io and its DNS record.
  • Open Viewers, and everything on their screens: they talk to their own Upstreams, which were not redeployed.
  • Earlier versions of the Worker, in Cloudflare’s version history.

Never touched

  • The other geenee deployment, geenee-dev.
  • The igv Upstream Worker and the igv Viewer’s Pages project.
  • The Juicebox Upstream Worker and the Juicebox Viewer’s Pages project.
  • The Spacewalk Upstream Worker and the Spacewalk Viewer’s Pages project.
  • Your working copy. The script builds from a commit in a throwaway checkout, so uncommitted changes never ship and your dist/ is not rewritten.

Two things do notice a deploy. A Workspace that is open drops its socket to geenee and rejoins within a few seconds. And it keeps running the old Workspace code until you reload the tab.

The Cloudflare pieces

Three Cloudflare products are in play across the four repositories. geenee uses two of them directly.

PieceWhat it isWho uses it
WorkerA program Cloudflare runs on every request to its address. It keeps nothing between requests. You replace it by uploading a new version with wrangler deploy.geenee, and each of the Upstreams
Durable ObjectThe object that holds state. A Worker finds one by name (here, a Room id); there is exactly one per name anywhere in the world, with its own small storage. Its code ships inside the Worker; its storage lives apart from the code and survives deploys.geenee’s Room; igv’s Room; Juicebox’s WebSocketRoom and McpSession; Spacewalk’s Room
PagesA project that holds uploaded static files and serves them at <project>.pages.dev, and optionally at a custom domain.The three Viewers only. geenee has no Pages project.

geenee’s Workspace page is a static asset of the Worker (Cloudflare calls this Workers Static Assets). It is uploaded with the Worker’s code in the same wrangler deploy, so the page and the Connector can never be out of step.

The object that holds state is the Durable Object. In geenee it is the class Room in src/room.ts. One instance exists per Room id. It holds the WebSockets of the Workspaces open in that Room, and stores a single value under the key lastUse: which Viewer the last tool call was for, so a Workspace opened later can bring that Viewer forward.

The Workspace page is not on Pages, even though it is a web page. It is a set of files that the geenee Worker itself serves. Pages appears in this story only as the home of the three Viewers that the Workspace frames.

Everything on the account

All four repositories deploy to one Cloudflare account, in the 3dg.io zone. Each one has its own deploy script, and each script touches only its own boxes.

Because geenee only forwards (ADR 0001), it holds no copy of the igv, Juicebox or Spacewalk tools. When an Upstream changes its tools, geenee picks them up on the next request with no geenee deploy. The reverse is also true: a geenee deploy can never change what an Upstream or a Viewer does.

What the script does, step by step

scripts/deploy-dev.sh my-branch       # dev: any branch, tag or commit
git tag prod-2026-11-12 main          # production: tag main,
git push origin prod-2026-11-12       # push the tag,
scripts/deploy.sh prod-2026-11-12     # and release it

scripts/deploy-dev.sh is scripts/deploy.sh pointed at the dev deployment; the steps are the same, except that dev takes any ref and production only a prod- tag on origin. A second release the same day is prod-2026-11-12.2.

StepWhat happens

3Installnpm ci: installs exactly what package-lock.json says, from scratch.
4Type-checknpm run typecheck: regenerates the Worker’s types from wrangler.toml, then type-checks the Worker and tests, and the Workspace separately.
5Testnpm run test:run: the whole suite, against stand-in Upstreams. No network.
6Buildnpm run deploy:prod (or deploy:dev) first runs vite build with CLOUDFLARE_ENV set to that environment of wrangler.toml, and with VITE_VERSION set to the version from scripts/version.sh: the ref’s tag or branch and its short commit. The worktree is detached, so the script hands it the ref it was given (for HEAD, the branch you are on): prod-2026-11-12 (a1b2c3d) for a release. Cloudflare’s Vite plugin writes two folders: dist/geenee/, the bundled Worker with a wrangler.json holding that environment’s settings, and dist/client/, the Workspace page.
7DeployThe same npm script then runs wrangler deploy, which uploads what step 6 built as a new version of the Worker and makes it live. See What one upload contains.
8CheckFirst, an MCP initialize to each Upstream that environment of wrangler.toml names: the version each reports is printed, or did not answer, as the record of what this release was checked against, and is printed before any check can fail. Then three requests to the live address. (a) An MCP initialize to /mcp: the version it reports must be this build’s, its tag or branch and short commit, or the script fails. (b) tools/list: counts the tools and prints the number. There is no fixed right number, as it grows when an Upstream adds tools; one that drops from the last release usually means an Upstream did not answer, which the versions printed first show. This one is never a failure. (c) open_geenee opens a Room, then GET /viewers for it: each Viewer address must be the page the script names for that deployment (its IGV_PAGE, JUICEBOX_PAGE and SPACEWALK_PAGE, listed in the table below), or the script fails. Check (c) needs all three Upstreams to be up.

After the upload it prints what each Upstream reported; when the checks pass, it names the build, the number of tools and the Viewer pages, then the Connector URL:

What one upload contains

wrangler deploy sends one bundle. Every item in it replaces the item of the previous version; none is merged with what was there.

ItemComes fromOn Cloudflare
Worker codesrc/*.ts and the MCP SDK, bundled into dist/geenee/index.jsReplaced. The whole Worker, including the Room class.
Static assetsindex.html, src/workspace/main.ts and workspace.css, built into dist/client/ with hashed file names such as assets/index-BBYCN2yg.jsReplaced as a set. Wrangler uploads only the files Cloudflare does not already have, but afterwards only the new set is served. An old hashed file name stops resolving.
Settings (vars)IGV_UPSTREAM_URL, JUICEBOX_UPSTREAM_URL and SPACEWALK_UPSTREAM_URL from the environment’s section of wrangler.tomlReplaced. A change to an Upstream address takes effect only with a deploy.
Durable Object bindingROOM → class RoomUnchanged in practice: the same binding each time.
Migration[[migrations]] tag = "v1": “Room is a Durable Object class with SQLite storage”Applied once, on the first deploy. Cloudflare remembers that v1 ran, so later deploys skip it.
Routegeenee.3dg.io or geenee-dev.3dg.io as a custom domainCreated, with its DNS record, on the first deploy. Kept after that.
VersionVITE_VERSION, written into both the Worker code and the Workspace JavaScript at build timeReplaced, because it is part of the code.
Loggingobservability.logs.enabled = trueKept on.

What is not in the bundle: any Room’s stored data, any secret (geenee has none), any igv, Juicebox or Spacewalk file, and any *.workers.dev or preview address (both are turned off, so each deployment has exactly one public address).

The top level of wrangler.toml, outside any [env.…], is for npm run dev only and is never deployed. A deploy reads only [env.prod] or [env.dev]. Named environments do not inherit vars or Durable Object bindings, which is why the file repeats them.

The moment it goes live

The new version takes all traffic within seconds of the upload. There is no gradual rollout. This is what each part sees:

PartWhat happens
A Host calling /mcpThe next request runs the new code. geenee keeps no state between MCP requests, so nothing is lost.
A Room Durable ObjectRestarted on the new code. Its open WebSockets are closed. Its storage, the lastUse report, is untouched.
An open WorkspaceIts socket to /ws drops. It rejoins after 1 s, then 2 s, and so on up to 5 s between tries. On rejoining it is told the last report again, and acts on it only if it had not seen it. It is still the old Workspace code: reload the tab to get the new page and the new version.
The Viewers inside itNot affected. Each is a frame loaded from its own Pages project and connected to its own Upstream, neither of which changed. The genome, the map and everything on screen stay as they were.
The model’s Room idStill good. A Room is found by name (idFromName(room)), so the same id reaches the same Room and the same storage on the new version.
The Host’s view of geeneegeenee asks the Upstreams for their tools afresh on every request. But a Host usually reads geenee’s tool list and server instructions when a conversation connects, so after changing tool names, descriptions or INSTRUCTIONS, start a new conversation to be sure the model sees them.

Durable Object storage is never rolled back. If you deploy an older version of the code, Rooms keep whatever the newer code stored. With today’s single lastUse value this does not matter.

production or dev

geenee has two deployments: production, the published Connector that people add to their Host, and dev, a single slot for trying a branch without touching production. Whichever ref was deployed to dev last is what it runs. They are two completely separate Workers. They share no code version, no Rooms, no storage and no Upstreams: production forwards to the prod Upstreams, dev to the dev ones (ADR 0004). Production runs only a prod- tag; dev runs whatever was deployed to it last. Only the script picks between them.

The Viewer pages are not configured in geenee at all. The Workspace asks geenee (/viewers), geenee asks each Upstream for its Join link, and the Upstream’s own settings decide which page that is. The deploy script names the pages only to check them, so when an Upstream moves its page, the script’s *_PAGE for each deployment that forwards to it changes too.

I changed X: what do I deploy?

Each repository deploys only itself, so a change is shipped by the script of the repository it lives in. A geenee deploy is needed only when geenee’s own code or settings change. The rows below put a change on dev; each Upstream reaches prod by its own tagged release (deploy-prod.sh in igvjs-mcp and spacewalk-mcp, deploy-view-prod.sh in juicebox-mcp), as geenee’s Deployments sets out.

The igv and Spacewalk dev scripts deploy from your working copy, not from a throwaway checkout, so uncommitted igv or Spacewalk changes do ship. The geenee and Juicebox scripts deploy from a commit.

An Upstream’s dev deploy reaches geenee dev only, and its prod release geenee production only, with no geenee deploy: geenee reaches each Upstream by its address and does not pin a version. So a change to any Upstream can be tried on geenee dev without production seeing it, and /versions is how to tell what is behind either geenee now.

Which build is live?

Every deploy is stamped with its version: the tag or branch it was built from and its short commit, for example prod-2026-11-12 (a1b2c3d) on prod and main (d4e5f6a) on dev. Both come from git at build time; nothing is bumped by hand. You can read it in four places:

  • The Workspace shows it at the right end of its tab bar, with the Connector URL. Remember that an open tab shows the build it was loaded with; reload to see the live one.
  • The Connector gives it as its version in the reply to initialize: 
    curl -s https://geenee.3dg.io/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":0,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"me","version":"0"}}}'
  • /versions, a page on each geenee (https://geenee.3dg.io/versions), gives its version and the version each Upstream behind it reports, asked as the page loads. An Upstream that does not answer is shown as such.
  • Cloudflare lists the Worker’s versions, newest first: npx wrangler deployments list --env prod (or --env dev).

Retiring an address

A deploy only ever creates or replaces. When a Deployment moves to a new address, or its Worker is renamed in wrangler.toml, the first deploy brings up a new Worker at the new address and leaves the old one running, still answering at its old address with whatever code it last had. Nothing in the repository mentions it again, so nobody notices. The rename to production and dev on 30 October 2026 left two such Workers, geenee-view-dev and geenee-test, serving a two-week-old /get page until 14 November.

So retire the old Worker in the same change that moves the address, once the new one has passed its checks. First remove its custom domain, in the Cloudflare dashboard under the Worker’s Settings, Domains & Routes. Then delete the Worker:

npx wrangler delete --name <old-worker>

This removes the Worker and its Rooms. It cannot be undone. Check afterwards that the old address answers like any unknown name: 3dg.io has a wildcard DNS record, so the name still resolves, but the request fails with a 5xx instead of reaching geenee.

curl -s -o /dev/null -w "%{http_code}\n" https://<old-address>/get    # 5xx, not 200 or 302

To see what is on the account, list its Workers in the Cloudflare dashboard, under Workers & Pages. Every geenee Worker other than geenee, geenee-dev and geenee-install is a leftover.

Shortcuts and traps

SituationWhat to know
You run npm run deploy:prod directlyIt builds and deploys your working copy, uncommitted edits included, with no tag, no type-check, no tests and no final checks. Production then runs something no tag names: don’t. Its version then has -dirty after the commit. It is the fastest loop, and also the easiest way to ship something you did not mean to. It writes your local dist/; the script does not.
Step 8 failsThe new build is already live. A version mismatch usually means the upload did not go through; a Juicebox or Spacewalk page mismatch usually means that Upstream is down or is pointing at another page.
The tool count droppedAn Upstream did not answer: its version reads did not answer. geenee still works with the others. Not a failure of the deploy.
You want to undo a releaseRelease the earlier tag again: scripts/deploy.sh prod-2026-11-05; git tag -l 'prod-*' lists them. Cloudflare can also roll back to a previous version (npx wrangler rollback --env prod), but releasing a tag keeps git as the record of what is live.
Someone else deploys after youBoth deployments are shared, and a deploy replaces the Worker for everyone. dev has one slot: agree who is using it. Try a branch on dev before it is merged and tagged for production.
scripts/deploy.sh main is refusedProduction takes only a prod- tag that is on origin. Tag the commit, push the tag, and run the script with it.
You rename or remove the Room classThat needs a new [[migrations]] entry in wrangler.toml, or wrangler deploy refuses. Changing what is inside Room needs none.
First deploy on a new machinenpx wrangler login with a login that can reach the account in wrangler.toml. There are no secrets to set.
The Workspace looks unchanged after a deployReload the tab. The page’s files are fetched once, when it opens.
The model does not use a renamed tool or new instructionsStart a new conversation in the Host.

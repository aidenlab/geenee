How geenee deploys

One run of scripts/deploy-test.sh replaces exactly one Cloudflare Worker: its code, the Workspace page it serves, and its settings. The Worker’s Durable Object storage is kept. Nothing that belongs to igv or Juicebox is touched. This document shows what is uploaded, what is replaced, what survives, and what to run when you change something elsewhere.

The short answer

Say you run scripts/deploy-test.sh view. This is what changes on Cloudflare:

Replaced

  • The code of the Worker geenee-view-dev: /mcp, /viewers, /connections, /ws, the tool renaming, the server instructions, open_geenee.
  • The Workspace page: index.html and its JavaScript and CSS, served by the same Worker.
  • The Worker’s settings: the two Upstream addresses, the binding to the Room Durable Object, logging.
  • The code of the Room Durable Object, which is part of the Worker.
  • The build number the Connector and the Workspace report.

Kept

  • Every Room’s storage: the last “Viewer used” report.
  • Room ids. A Room id the model already holds still finds the same Room.
  • The custom domain geenee-view-dev.3dg.io and its DNS record.
  • Open Viewers, and everything on their screens: they talk to their own Upstreams, which were not redeployed.
  • Earlier versions of the Worker, in Cloudflare’s version history.

Never touched

  • The other geenee deployment, geenee-dev (web).
  • The igv Upstream Worker and the igv Viewer’s Pages project.
  • Both Juicebox Upstream Workers and both Juicebox Viewer Pages projects.
  • Your working copy. The script builds from a commit in a throwaway checkout, so uncommitted changes never ship and your dist/ is not rewritten.

Two things do notice a deploy. A Workspace that is open drops its socket to geenee and rejoins within a few seconds. And it keeps running the old Workspace code until you reload the tab.

The Cloudflare pieces

Three Cloudflare products are in play across the three repositories. geenee uses two of them directly.

PieceWhat it isWho uses it
WorkerA program Cloudflare runs on every request to its address. It keeps nothing between requests. You replace it by uploading a new version with wrangler deploy.geenee, and each of the Upstreams
Durable ObjectThe object that holds state. A Worker finds one by name (here, a Room id); there is exactly one per name anywhere in the world, with its own small storage. Its code ships inside the Worker; its storage lives apart from the code and survives deploys.geenee’s Room; igv’s Room; Juicebox’s WebSocketRoom and McpSession
PagesA project that holds uploaded static files and serves them at <project>.pages.dev, and optionally at a custom domain.The two Viewers only. geenee has no Pages project.

geenee’s Workspace page is a static asset of the Worker (Cloudflare calls this Workers Static Assets). It is uploaded with the Worker’s code in the same wrangler deploy, so the page and the Connector can never be out of step.

The object that holds state is the Durable Object. In geenee it is the class Room in src/room.ts. One instance exists per Room id. It holds the WebSockets of the Workspaces open in that Room, and stores a single value under the key lastUse: which Viewer the last tool call was for, so a Workspace opened later can bring that Viewer forward.

The Workspace page is not on Pages, even though it is a web page. It is a set of files that the geenee Worker itself serves. Pages appears in this story only as the home of the two Viewers that the Workspace frames.

Everything on the account

All three repositories deploy to one Cloudflare account, in the 3dg.io zone. Each one has its own deploy script, and each script touches only its own boxes.

Because geenee only forwards (ADR 0001), it holds no copy of the igv or Juicebox tools. When an Upstream changes its tools, geenee picks them up on the next request with no geenee deploy. The reverse is also true: a geenee deploy can never change what an Upstream or a Viewer does.

What the script does, step by step

scripts/deploy-test.sh view           # deploys HEAD to geenee-view-dev
scripts/deploy-test.sh web            # deploys HEAD to geenee-dev
scripts/deploy-test.sh view my-branch # any branch, tag or commit
StepWhat happens
1Logged in?npx wrangler whoami. If you are not logged in to Cloudflare, the script stops and tells you to run npx wrangler login.
2Check outCreates a temporary directory and checks out the ref there with git worktree add --detach. The ref defaults to HEAD, your current commit. Uncommitted edits are not in it. The worktree is removed when the script exits, whether it succeeded or not.
3Installnpm ci: installs exactly what package-lock.json says, from scratch.
4Type-checknpm run typecheck: regenerates the Worker’s types from wrangler.toml, then type-checks the Worker and tests, and the Workspace separately.
5Testnpm run test:run: the whole suite, against stand-in Upstreams. No network.
6Buildnpm run deploy:view-dev (or deploy:dev for web) first runs vite build with CLOUDFLARE_ENV set to that environment of wrangler.toml, and with VITE_BUILD set to the build number from scripts/build-number.sh. Cloudflare’s Vite plugin writes two folders: dist/geenee/, the bundled Worker with a wrangler.json holding that environment’s settings, and dist/client/, the Workspace page.
7DeployThe same npm script then runs wrangler deploy, which uploads what step 6 built as a new version of the Worker and makes it live. See What one upload contains.
8CheckThree requests to the live address. (a) An MCP initialize to /mcp: the version it reports must contain this commit’s short hash, or the script fails. (b) tools/list: counts the tools and prints the number. 44 means both Upstreams answered; this one is not a failure if it is lower. (c) GET /viewers?room=0000000000: the Juicebox Viewer address must be this stack’s Juicebox page, or the script fails. Check (c) needs the Juicebox Upstream to be up.

When it succeeds, the last line names the build, the Connector URL, the number of tools, and the Juicebox Viewer page:

deployed build 24 (1c33760, 2026-10-22 10:41 EDT) of view to https://geenee-view-dev.3dg.io: …

What one upload contains

wrangler deploy sends one bundle. Every item in it replaces the item of the previous version; none is merged with what was there.

ItemComes fromOn Cloudflare
Worker codesrc/*.ts and the MCP SDK, bundled into dist/geenee/index.jsReplaced. The whole Worker, including the Room class.
Static assetsindex.html, src/workspace/main.ts and workspace.css, built into dist/client/ with hashed file names such as assets/index-BBYCN2yg.jsReplaced as a set. Wrangler uploads only the files Cloudflare does not already have, but afterwards only the new set is served. An old hashed file name stops resolving.
Settings (vars)IGV_UPSTREAM_URL and JUICEBOX_UPSTREAM_URL from the environment’s section of wrangler.tomlReplaced. A change to an Upstream address takes effect only with a deploy.
Durable Object bindingROOM → class RoomUnchanged in practice: the same binding each time.
Migration[[migrations]] tag = "v1": “Room is a Durable Object class with SQLite storage”Applied once, on the first deploy. Cloudflare remembers that v1 ran, so later deploys skip it.
Routegeenee-view-dev.3dg.io as a custom domainCreated, with its DNS record, on the first deploy. Kept after that.
Build numberVITE_BUILD, written into both the Worker code and the Workspace JavaScript at build timeReplaced, because it is part of the code.
Loggingobservability.logs.enabled = trueKept on.

What is not in the bundle: any Room’s stored data, any secret (geenee has none), any igv or Juicebox file, and any *.workers.dev or preview address (both are turned off, so each deployment has exactly one public address).

The top level of wrangler.toml, outside any [env.…], is for npm run dev only and is never deployed. A deploy reads only [env.dev] or [env.view-dev]. Named environments do not inherit vars or Durable Object bindings, which is why the file repeats them.

The moment it goes live

The new version takes all traffic within seconds of the upload. There is no gradual rollout. This is what each part sees:

PartWhat happens
A Host calling /mcpThe next request runs the new code. geenee keeps no state between MCP requests, so nothing is lost.
A Room Durable ObjectRestarted on the new code. Its open WebSockets are closed. Its storage, the lastUse report, is untouched.
An open WorkspaceIts socket to /ws drops. It rejoins after 1 s, then 2 s, and so on up to 5 s between tries. On rejoining it is told the last report again, and acts on it only if it had not seen it. It is still the old Workspace code: reload the tab to get the new page and the new build number.
The Viewers inside itNot affected. Each is a frame loaded from its own Pages project and connected to its own Upstream, neither of which changed. The genome, the map and everything on screen stay as they were.
The model’s Room idStill good. A Room is found by name (idFromName(room)), so the same id reaches the same Room and the same storage on the new version.
The Host’s view of geeneegeenee asks the Upstreams for their tools afresh on every request. But a Host usually reads geenee’s tool list and server instructions when a conversation connects, so after changing tool names, descriptions or INSTRUCTIONS, start a new conversation to be sure the model sees them.

Durable Object storage is never rolled back. If you deploy an older version of the code, Rooms keep whatever the newer code stored. With today’s single lastUse value this does not matter.

web or view

geenee has two deployments because juicebox-mcp has two dev stacks, one per Juicebox page. They are two completely separate Workers. They share no code version, no Rooms and no storage. Only the argument to the script picks between them.

I changed X: what do I deploy?

Each repository deploys only itself, so a change is shipped by the script of the repository it lives in. A geenee deploy is needed only when geenee’s own code or settings change.

geenee: the Connector, routing, renaming, instructions, the Roomgeenee/scripts/deploy-test.sh <web|view>One geenee Worker, with its Workspace page

The igv script deploys from your working copy, not from a throwaway checkout, so uncommitted igv changes do ship. The geenee and Juicebox scripts deploy from a commit.

The igv stack has one dev deployment, shared by both geenee deployments, so an igv deploy reaches both at once. The Juicebox stacks are paired with geenee one to one: deploy Juicebox’s view stack to test with geenee-view-dev, and its web stack to test with geenee-dev.

Which build is live?

Every deploy is stamped with a build number: the commit count, the short hash, and the time of the build, for example 24 (1c33760, 2026-10-22 10:41 EDT). The count and hash say which code; the time says which deploy. You can read it in three places:

  • The Workspace shows it at the right end of its tab bar, with the Connector URL. Remember that an open tab shows the build it was loaded with; reload to see the live one.
  • The Connector gives it as its version in the reply to initialize: 
    curl -s https://geenee-view-dev.3dg.io/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":0,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"me","version":"0"}}}'
  • Cloudflare lists the Worker’s versions, newest first: npx wrangler deployments list --env view-dev.

Shortcuts and traps

SituationWhat to know
You run npm run deploy:view-dev directlyIt builds and deploys your working copy, uncommitted edits included, with no type-check, no tests and no final checks. The build number then ends in -dirty. It is the fastest loop, and also the easiest way to ship something you did not mean to. It writes your local dist/; the script does not.
Step 8 failsThe new build is already live. A version mismatch usually means the upload did not go through; a Juicebox page mismatch usually means the Juicebox Upstream is down or is pointing at another page.
The tool count is below 44An Upstream did not answer. geenee still works with the other one. Not a failure of the deploy.
You want to undo a deployRun the script again with the earlier commit: scripts/deploy-test.sh view <ref>. Cloudflare can also roll back to a previous version (npx wrangler rollback --env view-dev), but redeploying a ref keeps git as the record of what is live.
Someone else deploys after youThe dev deployments are shared, and a deploy replaces the Worker for everyone. Agree who is testing.
You rename or remove the Room classThat needs a new [[migrations]] entry in wrangler.toml, or wrangler deploy refuses. Changing what is inside Room needs none.
First deploy on a new machinenpx wrangler login with a login that can reach the account in wrangler.toml. There are no secrets to set.
The Workspace looks unchanged after a deployReload the tab. The page’s files are fetched once, when it opens.
The model does not use a renamed tool or new instructionsStart a new conversation in the Host.

The words used here (Host, Connector, Upstream, Viewer, Workspace, Room) are defined in GLOSSARY.md. How the parts talk to each other once deployed is in How geenee works. The Juicebox side of deploying is covered in more depth by docs/how-juicebot-deploys.html in juicebox-mcp.

geenee’s Deployments

geenee and each of its three Upstreams run twice: once as prod, the copy people use, and once as dev, a slot for trying a change. This page lists every address, how to put a change on each, and how to tell what is running.

Being rolled out. This page describes where we are going (ADR 0004). Until the last step of the rollout, geenee prod still forwards to the dev Upstreams, and the old dev names (igv-bot-…, juicebot-view-…) are still live.

The four rules

  1. prod talks to prod, dev talks to dev. geenee prod forwards only to the prod Upstreams, geenee dev only to the dev ones. There is no switch.
  2. Addresses never change; what is behind them does. geenee does not pin a version of an Upstream. It uses whatever that Upstream’s Deployment is running.
  3. prod changes only from a tag. Every prod release is a tag on main, and rolling back is releasing an earlier tag. dev takes any branch, at any time.
  4. Every Deployment says what it runs. Ask any of them and it answers with its tag (or branch) and commit. geenee also tells you what each Upstream behind it is running.

Trying a change on dev

Each dev Deployment is a single slot: whatever was deployed to it last is what it runs. Deploy the Upstream you changed, then try it through geenee dev, https://geenee-dev.3dg.io/mcp.

Run, from that repositoryDeploys
geeneescripts/deploy-dev.sh [ref]geenee dev at any branch, tag or commit (default HEAD)
igvscripts/deploy-dev.shthe igv Worker and Viewer, from your working copy
Juiceboxscripts/deploy-dev.sh <juicebox-view clone> [ref]the Juicebox Worker and the juicebox-view page
Spacewalkscripts/deploy-dev.shthe Spacewalk Worker and Viewer, from your working copy

The Juicebox dev Deployment is shared with Juicebot: it is also where Juicebot changes are tried before a Juicebot release. Expect it to move.

Releasing to prod

A release is a tag. The tag names the date, with .2, .3 … for a second release the same day.

  1. Merge the change to main, after trying it on dev.
  2. Tag main and push the tag. Where a Viewer lives in a second repository, tag that one too, with the same name.
  3. Run the repository’s prod script with the tag. It checks the tag out into a throwaway copy, tests it, deploys the Worker and its Viewer, and checks that the live Deployment reports that tag.
TagInRun
geeneeprod-YYYY-MM-DDgeeneescripts/deploy.sh prod-YYYY-MM-DD

Juiceboxview-prod-YYYY-MM-DDjuicebox-mcp and juicebox-viewscripts/deploy-view-prod.sh view-prod-YYYY-MM-DD
Spacewalkprod-YYYY-MM-DDspacewalk-mcp and spacewalkscripts/deploy-prod.sh prod-YYYY-MM-DD

For example, releasing Spacewalk on 12 November:

git -C spacewalk-mcp tag prod-2026-11-12 main && git -C spacewalk-mcp push origin prod-2026-11-12
git -C spacewalk     tag prod-2026-11-12 main && git -C spacewalk     push origin prod-2026-11-12
cd spacewalk-mcp && scripts/deploy-prod.sh prod-2026-11-12

Juicebox’s tags start with view-prod- because juicebox-mcp also releases Juicebot, with plain prod- tags. A tag names exactly one release.

A change to an Upstream and geenee

geenee forwards an Upstream’s tools as they are, so most Upstream changes need nothing from geenee: release the Upstream and geenee prod offers the change on the next request.

When geenee itself depends on what changed (a tool open_geenee uses, the Viewer page, the Room), try both on dev together, then release in this order:

  1. The Upstream to prod, in a form the current geenee prod still works with.
  2. geenee to prod.
  3. If the Upstream kept something only for the old geenee, remove it in a later Upstream release.

What is running right now?

Every Deployment gives what it runs as its version: a tag and commit on prod, a branch and commit on dev.

prod-2026-11-12 (a1b2c3d)
main (d4e5f6a)

To see everything behind geenee at once, open /versions on either geenee:

https://geenee.3dg.io/versions
https://geenee-dev.3dg.io/versions

It asks each Upstream as you load it, so it is never out of date. scripts/deploy.sh prints the same list at the end of each geenee release, which is a record of what that release was checked against. The version an Upstream gives covers its Viewer too, since they are released together.

To ask one Deployment directly, without geenee:

curl -s -X POST https://spacewalk-mcp.3dg.io/mcp \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":0,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"me","version":"0"}}}' \
  | grep -o '"serverInfo":{[^}]*}'

Rolling back

Run the same prod script with the earlier tag. git tag -l 'prod-*' (or 'view-prod-*') lists them. dev never needs rolling back: deploy whatever you want it to run.

Juicebot is not ours

juicebox-mcp also releases Juicebot production, https://juicebot-mcp.3dg.io/mcp and https://juicebot.3dg.io/, with scripts/deploy-prod.sh and prod- tags. It runs the same code as geenee’s Juicebox Upstream, but it is a separate product with its own releases and its own users. geenee never forwards to it, and nothing on this page touches it.

The rollout

Done in this order, each step checked before the next. geenee prod keeps working on the dev Upstreams until step 4, the only step people using geenee will notice.

StepWhat changes
1Versionsgeenee and each Upstream report their tag or branch and commit.
2dev renamesNew dev Deployments under the new names; geenee dev pointed at them; the old igv-bot-… and juicebot-view-… dev Deployments deleted.
3prod Upstreamsigv prod created, Spacewalk’s first prod release, Juicebox view-prod created. Each checked on its own.
4geenee cutovergeenee prod released, forwarding to the prod Upstreams, with /versions and tag-only releases.
